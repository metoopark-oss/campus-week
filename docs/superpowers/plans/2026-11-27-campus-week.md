## 내부 상태와 함수 약속

모두 추후 `index.html`의 내부 스크립트에 둔다. 아래는 인터페이스 명세이며 실행 코드는 아니다.

- `Stats`: `study`, `health`, `happiness` 숫자 세 개.
- `Choice`: `label` 문자열과 `delta: Stats`.
- `DayEvent`: `day` 요일, `title` 사건, `choices` 두 개(A, B 순서).
- `HistoryEntry`: `dayIndex`, `choiceIndex`, `label`, 복사한 `before: Stats`, `after: Stats`, `actualDelta: Stats`.
- `Ending`: `재충전 필요`, `균형 달인`, `아슬아슬 생존` 중 하나.
- `GameState`: `phase`는 `start | choice | result | ending`, `dayIndex`는 0~6, `stats: Stats`, `history: HistoryEntry[]`, `ending: Ending | null`. 선택 잠금은 `phase`와 해당 날짜의 기록 존재 여부로 판단하여 별도 잠금 값과 어긋나지 않게 한다.
- `EVENTS`: CSV의 7개 행을 순서대로 옮긴 고정 데이터. 실행 중 수정하지 않는다.
- `createInitialState() -> GameState`: 시작 화면, 월요일 인덱스, 50/50/50, 빈 기록, 엔딩 없음.
- `applyChoice(stats: Stats, delta: Stats) -> { after: Stats, actualDelta: Stats }`: 원본 상태를 변경하지 않고 합산·0~100 제한·실제 차이 계산.
- `getEnding(stats: Stats, dayIndex: number) -> Ending | null`: 0 판정 우선, 일요일이면 40 기준 판정, 그 외에는 없음.
- `choose(dayIndex: number, choiceIndex: number) -> void`: 현재 날짜와 선택 단계인지 검증한 뒤 하루 선택을 한 번 처리.
- `advance(dayIndex: number) -> void`: 결과 단계·날짜 일치를 확인한 뒤 다음 날 선택 또는 일요일 엔딩 표시로 이동. 능력치·기록을 변경하지 않는다.
- `startGame() -> void`, `restartGame() -> void`: 각각 새 상태에서 월요일 선택으로 진입, 새 상태의 시작 화면으로 복귀.
- `render() -> void`: 상태를 읽어 표시만 갱신한다. 기록된 `before`·`after`를 수정하지 않는다.

## 작업 2: 원본 데이터와 선택·판정 처리

**Files:** 추후 `index.html` 내부 스크립트 수정.

**Interfaces:** 위 명세의 데이터 형식, `EVENTS`, `createInitialState`, `applyChoice`, `getEnding`, `choose`를 만든다. 작업 3은 이 상태와 함수를 사용한다.

- [ ] `BRIEF.md`의 CSV 7행을 `EVENTS`로 옮긴다. 요일·사건·선택 문구와 A/B의 능력치 순서를 원본과 행별로 대조한다.
- [ ] `createInitialState()`를 정의하고 최초 로드 시 이 상태만 사용한다. 저장소·쿠키·서버 통신은 사용하지 않는다.
- [ ] `applyChoice()`에서 세 능력치를 합산하고 각각 0~100으로 제한한다. `actualDelta`는 제한 후 수치에서 이전 수치를 뺀 값이다.
- [ ] `getEnding()`에서 하나라도 0인지 먼저 확인한다. 모두 양수이고 `dayIndex`가 6일 때만 전부 40 이상인지 확인한다. 다른 날은 엔딩 없음으로 반환한다.
- [ ] `choose()`는 현재 선택 단계, 현재 날짜 일치, 유효한 A/B 인덱스, 그 날짜의 미선택을 확인한다. 유효하면 입력을 잠그고 복사한 전후 수치·선택을 한 번 기록하고, 수치 반영과 판정을 끝낸 뒤 표시한다. 비동기 지연을 두지 않는다.
- [ ] `재충전 필요`이면 즉시 엔딩 단계로 전환한다. 나머지는 결과 단계로 전환하며, 일요일의 생존 엔딩은 이때 확정해 상태에 보관한다.
- [ ] 수동 검토: 50에 +60이면 100·실제 +50, 10에 −25이면 0·실제 −10인지 계산식과 표시 값을 대조한다. 일요일 40/40/40은 균형 달인, 39/40/40은 아슬아슬 생존, 0/100/100은 재충전 필요인지 분기 순서를 확인한다. 이 경계 검토를 위한 코드나 파일을 추가하지 않는다.
- [ ] 수동 동작 확인은 작업 3 연결 후 수행한다. 선택 버튼을 빠르게 반복 입력해 수치와 날짜별 기록이 한 번만 갱신되는지 확인한다.

## 작업 3: 화면 전환·결과·엔딩·초기화 연결

**Files:** 추후 `index.html` 내부 스크립트와 화면 영역 수정.

**Interfaces:** 작업 2의 상태와 선택 함수를 사용해 `render`, `advance`, `startGame`, `restartGame`을 구현한다.

- [ ] `render()`에서 현재 단계에 해당하는 영역만 표시한다. 선택 단계에는 요일·1~7일 진행도·현재 수치·원본 사건·두 선택지와 각각의 전체 변화량을 보여 준다.
- [ ] 선택 처리 후에는 버튼을 비활성화하거나 제거한다. 결과에는 선택 문구, 전후 수치와 실제 변화량을 보여 준다. 원본 효과와 실제 차이가 다르면 0~100 제한 설명을 붙인다.
- [ ] 월~토 결과에서는 `다음 날`, 일요일 생존 결과에서는 `엔딩 보기`를 표시한다. `advance()`는 현재 결과의 날짜를 검증하고 한 번만 이동한다. 버튼 표시나 화면을 다시 그리는 동작은 효과를 재적용하지 않는다.
- [ ] 엔딩에는 정확한 엔딩 이름, 큰 최종 수치, 작은 요일별 선택 문구를 표시한다. 즉시 종료일에는 마지막 선택의 결과도 보여 주고, 이후 날짜는 기록에 넣지 않는다. 엔딩에서 선택·다음 날 동작을 받지 않는다.
- [ ] `restartGame()`으로 모든 진행 상태를 새로 만들고 시작 화면으로 복귀시킨다. `startGame()`도 초기 상태에서 월요일 선택을 시작한다.
- [ ] 단계가 바뀌면 해당 제목으로 키보드 초점을 이동하고, 이전 화면의 버튼이 입력을 받지 않게 한다. 이벤트 처리기는 반복 등록하지 않으며, 날짜가 붙은 입력은 현재 날짜와 대조한다.
- [ ] 수동 확인: 결과 화면에서 기다려도 날짜가 바뀌지 않고, 다음 날 버튼을 반복 입력해도 날짜를 건너뛰지 않는지 확인한다. 엔딩에서 다시 시작한 뒤 50/50/50과 빈 기록으로 월요일이 시작되는지 확인한다.

### 2026-11-27 구현 기록

- 사용자의 별도 구현 요청에 따라 작업 1~3의 게임 코드를 프로젝트 루트 `index.html`에 작성했다. 구현 파일은 UTF-8 단일 HTML이며 스타일·스크립트·원본 CSV를 모두 포함한다.
- 작업 2의 검토를 코드 읽기로 수행했다. 선택은 선택 단계·해당 날짜·미기록 조건에서만 처리하고, 제한 후 0 판정을 7일 생존 판정보다 우선하며, 40은 성공 기준에 포함한다. 화면 표시와 다음 날 이동은 효과를 적용하지 않는다.
- 원본 CSV를 추출해 `BRIEF.md`와 `diff -u`로 대조했고 차이가 없었다. 내장 스크립트는 `node --check` 구문 검사를 통과했다. `file -I`에서 UTF-8 HTML임을 확인했다.
- 외부 주소·리소스 요청·저장소 사용이 없는지 코드에서 확인했다. 390px용 너비·줄바꿈·글자와 버튼 크기를 코드로 검토했다. 실제 화면을 확인했다는 의미는 아니다.
- 하위 에이전트 없이 작성자가 별도 코드 검토를 수행했다. Git·테스트 코드·서버·설치·배포는 사용하지 않았다.
- 작업 4의 브라우저 플레이와 390px 시각 검증은 미실행이다. 내장 브라우저가 보안 정책상 `file://` 프로토콜을 차단하여 로컬 파일 열기가 거부되었으며, 우회하지 않았다. 위 수동 확인 체크박스는 실행 증거 없이 완료 표시하지 않는다.
- 현재 산출물은 구현된 게임 파일이며, 실제 브라우저 플레이 검증은 남아 있다. 사용자는 `index.html`을 더블클릭해 열 수 있다.
